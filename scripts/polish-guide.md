# 语言 polish 规范（所有章节/文档共用）

目标：把这份技术研究润色得**深入浅出、易读、门槛低**——让不熟悉该项目的读者也能跟上，同时**一分准确性都不损失**。

## 可以做（鼓励）
- **降门槛**：术语（Cordis、waterfall、effect/disposer、seam、event-sourcing、MoE…）第一次出现时，用一句大白话解释"它到底是什么/解决什么"。
- **举例子/打比方**：为抽象机制补一个**具体、贴切**的小例子或类比（如"能力接缝像插座标准：换灯泡不用改电路"）。类比要准确、不夸张，且点到为止。
- **加'为什么重要'**：在硬核段落后补一句"这意味着…/对使用者来说…"，把机制与实际价值连起来。
- **开头钩子**：每章开头可用一句贴近读者的问题或场景引入（章内已有"读完能回答…"的可保留/优化）。
- **拆长句、去术语堆砌**：把又长又绕的句子拆短；被动/名词化改成主动、具体。
- **过渡更顺**：段落之间加轻量过渡，让叙事连贯。

## 绝不能动（硬约束）
- **所有 `文件:行号` 源码引用**：一字不改、不删、不挪。
- **所有 `[verified]` / `[inferred]` / `[claimed]` 证据标记**：保留原位与原级别。
- **所有 ratify-note 块**：保留（可微调其内散文使更易读，但候选/理由/证据等级/残余风险的**事实与结论不变**）。
- **所有 mermaid 图（含白底 div 包裹）与图注**：不改代码、不改结论。
- **任何数字、事实、机制结论**：commits 数、包数、事件名、类型名、默认值等一律不变。
- **不得重新引入**：研究方法自述（工程化方法 / ratify-loop / review-loop / 七维 / 工作流 / git-repo-deepresearch）、"源码基线/提交区间/研究日"这类元信息 banner。
- **不得使用过强措辞**：最精妙 / 必然选择 / 极致 / 完美无缺 / 毫无疑问。
- **不改章节标题与各级小标题**（可优化标题下第一句导语）。守证据边界：动机类判断仍用「可能/或许/不排除」。

## 风格
- 现状陈述、先事实后解释再判断；克制修辞。
- 中文技术写作，专有名词/代码保留英文与反引号。
- 篇幅可持平或略增（补例子/解释），不要为凑字数灌水，也不要删内容。

## 输出
用 Edit 就地修改给定文件（可多次 Edit）。完成回一句：润色了哪些方面、是否保留了全部引用/图/ratify-note。
